# AGENTS.md

Desktop GUI (PySide6) for the ORGBRO T003 USB thermal label printer.

## Commands

```bash
python -m venv --system-site-packages .venv   # PySide6 comes from the system package
.venv/bin/pip install -e '.[dev]'               # [dev] = pytest + PySide6; plain `pip install -e .` is the Qt-free core/CLI
.venv/bin/t003-gui                            # run the app
.venv/bin/t003-print "text" --qr URL          # CLI (same options as the GUI; --preview out.png to not print)
.venv/bin/pytest                              # tests (no printer needed)
packaging/install.sh                          # KDE launcher, icons + ~/.local/bin/print-label wrapper
.venv/bin/t003-gui --selftest                 # verifies fonts/licences/assets/libusb/render (also what CI runs on built apps)
python packaging/build.py                     # PyInstaller build for the current OS (dist/); make_appimage.sh wraps the Linux one
```

## Scope (read before adding anything)

This is a hobby app: a fun, Y2K-flavoured label studio for cheap thermal printers (see README, "What this is"). A change
should be **fun**, or **small and useful**. Roadmap items carry tags (`fun`, `useful`, `polish`, `infra`, `research`,
`big`); prefer `fun` and `polish`, treat `big` as "only if it's fun to build and cheap to keep working", and don't start
`infra` items (new platforms, PyPI) unless someone asks. Don't grow the build or CI further: it was scaled back on
purpose. Put creative effort into the *labels* (effects, stickers, frames, fonts) before the app's own chrome.

## Compatibility (keep these true)

- **Python 3.9+.** No 3.10-only syntax in `src` (`from __future__ import annotations` everywhere; no `match`, no `zip(strict=)`, no `tomllib` in code or tests). CI runs the oldest (3.9) and newest (3.13) Python plus an oldest-libraries job on 3.10; the versions in between are not tested individually.
- **Qt is optional.** `core`, `render`, `imaging`, `composition`, `presets`, `cli` never import PySide6; `pip install .` (no extra) is a working CLI. `t003-gui` goes through `launcher.py`, which prints what to install if PySide6 is missing (and re-raises any *other* ImportError). Tests that need Qt `importorskip("PySide6")`; `tests/test_packaging.py` runs the CLI with PySide6 blocked. Don't import Qt from a Qt-free module.
- **Lower bounds are tested**: CI's `minimum-versions` job installs PySide6 6.5.3, Pillow 9.1.0, pyusb 1.2.1, libusb-package 1.0.30, qrcode 7.4, fontTools 4.30. (libusb-package < 1.0.30 looks fine on a dev machine, which has a system libusb, but pyusb rejects it on a clean one: only CI caught it.) Raise a bound in `pyproject.toml` only together with that job. `QFormLayout.setRowVisible` is why Qt >= 6.4.
- **A wheel needs every data file in `package-data`** (fonts, licences, `assets/*`); an editable install hides a missing one. `test_package_data_covers_every_asset_and_font` and CI's `package` job (build wheel, install it clean, run `--selftest`) guard this.
- `libusb-package` is only required where it has wheels (Windows, macOS, Linux x86-64/arm64); elsewhere `core._backend()` falls back to the system libusb.

- **Release floors are measured, not claimed**: the Linux AppImage is built inside AlmaLinux 8 with a python-build-standalone Python and `packaging/check_glibc.py --max 2.28` fails the build otherwise (PyInstaller bundles the *build machine's* libraries and libpython, so on the ubuntu-22.04 runner the floor was glibc 2.35, not what Qt's wheels need); the macOS builds run `packaging/check_macos_min.py --max 12.0`. Qt is pinned to 6.8.3 for the binaries in `packaging/build-constraints.txt` (the newest wheels need macOS 14+ / glibc 2.34+). Raising a floor means changing those numbers on purpose, and the README table with them. `smoke-linux` runs the AppImage's self-test in three distro containers (Ubuntu 20.04, Debian 12, Fedora) before anything is published; it was eight, and was scaled back on purpose.

## Layout

- `src/t003gui/spec.py` — `LabelSpec` dataclass (everything a label can be) plus geometry constants and the allowed choices (`EFFECTS`, `BACKGROUNDS`, `BORDER_STYLES`, …). Presets are `asdict(LabelSpec)`, so new fields must have defaults.
- `src/t003gui/render.py` — Qt-free drawing: fonts via fontconfig (`font_path` resolves family→file; variable fonts load at their default weight so `_apply_weight` sets the weight axis for the bold toggle; `list_font_families` feeds the GUI picker), auto-fit text layers (shadow/outline/3D/glitch/neon/scanlines, synthetic italic), backgrounds (cached, seeded RNG so they are stable), borders, hazard bars, QR. Effect parameters scale with font size; glitch drops its fringe/gaps below ~24/30 dots because small text turns to mush. Text is positioned by measured ink bounds, not Pillow's bbox (side-bearings). Lines are laid out by `_layout` with a fixed pitch — never use `multiline_text` with `stroke_width`: Pillow widens the pitch by 2×stroke per line, so stroked passes (outline/3D/neon/halo) drift off the unstroked fill on lines 2+ (regression test in tests/test_render.py). Over a background pattern text gets a white halo. Nothing may be drawn below `SH` (tests enforce it).
- `src/t003gui/fonts.py` + `fonts/` — the **bundled** OFL fonts (23 families incl. DejaVu, ~20 MB, licences in `fonts/LICENSES/`), grouped by category for the GUI. `font_path` prefers these over fontconfig, so labels print identically on any machine. To add one: put the .ttf and its `LICENSE.<slug>` in `fonts/`, add a `BundledFont` entry; `tests/test_fonts.py` checks files, licence, coverage flag and Japanese support.
- **Japanese:** none of the Latin display fonts have kana/kanji. `render._FontSet` picks a font per glyph (cmap via fontTools): the primary font if it covers the character, else the bundled `Zen Kaku Gothic New` fallback; text is split into runs sharing one baseline (anchor `ls`). Fonts flagged `ja=True` cover Japanese in their own style (DotGothic16, Yusei Magic, Dela Gothic One, Stick, Zen Kaku). Any new bundled font must still print Japanese (test enforces).
- `src/t003gui/core.py` — sends a TSPL payload over USB with pyusb (`send`, `print_label`) and the label export helpers; re-exports spec/render/protocol names so callers use `core.X`.
- `src/t003gui/protocol.py` — Qt- and USB-free: `tspl(spec)` (the one place the TSPL payload is built), `STATUS_QUERY`, `STATUS_FLAGS`, `status_problems`. Any transport (USB now; Bluetooth, the web build) sends these bytes.
- `src/t003gui/bluetooth.py` — Qt- and USB-free Bluetooth: `send(payload, address)` (RFCOMM, same return as `core.send`), `resolve` (address or `""`/`"auto"` -> the first T003 `known_printers()` finds via `bluetoothctl`, after one `scan()` of `SCAN_SECONDS` if the system hasn't seen it, because BlueZ only lists devices it has discovered), and the `BLE` UUIDs/chunk/gap that the web client reads from `api.options()`. All transport timings live here so every client uses the same ones; tests use a fake socket (`connect=` is injectable). `core.print_label(spec, bluetooth=None)` is the one routing point (GUI and CLI both go through it); how the printer is reached is a *setting* (QSettings `connection`/`btAddress`, `OutputPanel.bluetooth_target()`), never part of a `LabelSpec`.
- `src/t003gui/form.py` — the label's simple controls as data (`FIELDS`, `TABS`, shipped to clients in `api.options()["form"]`; `web/form.js` renders them). **A new `LabelSpec` field must be added here or to `PENDING`, or `tests/test_form.py` fails**: that is what keeps every client's controls in step. A background/effect/border added in `spec.py` needs nothing here.
- `src/t003gui/settings.py` — Qt-free remembered settings (one JSON file next to the presets) for the web UI's desktop shell.
- `src/t003gui/bridge.py` — the desktop shell's side of the web UI (`Bridge`: `options`, `preview` as `{pixels (base64), hints}`, `print_label` returning `{problems, error}`, `known_printers`, `get_setting`/`set_setting`); pywebview exposes it to the page. No Qt, no pywebview, so it is tested plainly.
- `src/t003gui/api.py` — the client-neutral surface the web build drives (and a future desktop shell could): `label_from_json`, `preview_pixels` (W×H bytes, 0/255), `tspl_bytes`, `fonts_needed` (which bundled font files a label can open, for lazy loading), `options` (JSON of every choice, the geometry and the fonts, so a client builds its controls from it). Plain data in and out, no Pillow objects. Keep it that way: it is what keeps "one UI for both" possible later. `tests/test_api.py` checks it imports without Qt or USB.
- `src/t003gui/app.py` — the Qt window: arranges the panels (tabs: Content / Font / Image / Decoration / Doodle, plus the Output box; the tab is "Font", not "Text", so it is not confused with the text field on Content), the preset bar, the preview and the Print button, and handles drag-and-drop/paste of images. Live preview uses `core.to_bitmap`, so it shows exactly what will print. `MainWindow.spec()` / `set_spec()` just merge/dispatch to the panels. The font picker is an editable combo showing the curated bundled set by default (grouped, previewed in each font; "Show all installed fonts" switches to `core.list_font_families()`, fontconfig names), NOT QFontComboBox: Qt lists variable-font instances as bogus families ("Akatab Black") and foundry duplicates that fontconfig cannot resolve. Supports drag-and-drop of image files and named presets.
- `src/t003gui/panels.py` — the editing controls as self-contained widgets (`ContentPanel`, `TextPanel`, `ImagePanel`, `DecorationPanel`, `DoodlePanel`, `OutputPanel`). Each owns its widgets, maps its slice of `LabelSpec` via `read()`/`write(spec)` and emits `changed`; a test checks that every spec field belongs to exactly one panel. Layout is the window's job, so a new layout (side modules etc.) only rearranges panels. A new `LabelSpec` field goes into a panel's `read`/`write`.
- `src/t003gui/theme.py` — the `Theme` dataclass (colours, bevels, radii as CSS fragments), the built-ins `Y2K_BLUE`, `Y2K_PINK` (a `dataclasses.replace` of blue: colours only), `GUNMETAL` and `HANDHELD` (four olive shades only, flat, Pixelify Sans at `font_pt=11` because pixel fonts need their design size; `preview_tint` colours the preview pixmap, cosmetic only) in `THEMES`, one `stylesheet(theme)` template, and the `Banner` widget (styled by `Theme.banner`). The stylesheet is set on the **main window**, never the app, and the image file dialog is opened unparented: that keeps the system dialog unstyled (a parented dialog inherits the sheet). Choice is stored in QSettings (`theme`: a key or `system`; the old `y2k` bool is migrated). To add a theme: fill in a `Theme`, add it to `THEMES` (the View > Theme menu is built from that). QSS can't draw triangles, so arrow PNGs live in `assets/` (`arrow-*.png` navy, `arrow-*-lcd.png` green, selected by `Theme.arrow`; generated by `packaging/make_icons.py`, as are the icons). Don't name a widget attribute after a QWidget method (`self.size` once shadowed `QWidget.size()`; a test guards this).
- `src/t003gui/selftest.py` — `--selftest`; set `T003_SELFTEST_LOG` to also write to a file (windowed Windows builds have no console).
- `src/t003gui/widgets.py` — `SliderSpin` (a slider plus a value box; the **spin box is the source of truth**, so `value()`/`setValue()`/`valueChanged` behave like a QSpinBox; double-click the slider to reset; every box has one fixed width so all sliders are the same length) and `TenthsSpinBox`. Gamma uses `log_mapping(..., neutral=10)`: two log scales meeting exactly in the middle, so the neutral 1.0 is at the same spot as the 0 of the symmetric brightness/contrast sliders (one log scale put it a few pixels off; a test pins all three to the centre). Pixelate's default (Off) is its minimum, so that one is at the left end by nature. The themes style `QSlider` from their existing fields (`slider_fill`, `slider_handle` override where the defaults don't read, e.g. Handheld).
- `src/t003gui/imaging.py` — Qt-free picture pipeline for image labels: load (EXIF-upright, transparency over white) -> fit -> tone (gamma, brightness, contrast) -> dither. `load_gray` caches the decoded photo per (path, mtime, size) because decoding was ~70 of ~85 ms and the preview re-renders on every slider step (now ~13 ms); the cached image is shared, so never modify it in place. Default Floyd–Steinberg is left to `to_bitmap`; ordered (Bayer 4×4/8×8, built with Pillow ops, no numpy) and the hard cutoff produce pure 0/255 here, which `to_bitmap` passes through untouched. `LabelSpec.threshold` (not None) means hard cutoff and wins over `dither`; the Image tab maps that onto one combo. Looks (`mirror`, `flip`, `invert`, `pixelate`): with `pixelate` the tone and dither run at the low resolution and the dots are then enlarged (nearest), so the dither pattern itself is chunky; this is why `_dither(final=False)` forces Floyd–Steinberg early. `ImagePanel` dims itself until an image is chosen and hides the Cutoff row unless the hard cutoff is selected (keeps the tab, and so the window, short).
- **Image + text** (`LabelSpec.image_layout`, `image_size`): `"only"` (default) keeps the old behaviour (the picture replaces text/QR, `render` returns early). `left/right/top/bottom` carve `image_size` % (clamped 20-80) of the usable area out of `ax0/ax1/ay0/ay1` before the QR and text lay out in what is left, so QR and text need no special cases. `behind` pastes the picture covering the whole sticker (`ImageOps.fit`) and turns on the same white text halo that backgrounds get (the `backdrop` flag); it replaces the background pattern. Controls live on the Content tab (shortest page, so the window doesn't grow); the combo uses `AdjustToMinimumContentsLength` because a long item widens the whole window.
- **Text layout is pinned to Pillow's BASIC engine** (`render._font`, `layout_engine=ImageFont.Layout.BASIC`). Raqm, when the Pillow build has it, kerns differently and draws some fonts heavier, so labels depended on each machine's Pillow, and Pyodide's Pillow (the web build) has no Raqm. With the pin the desktop matches Pyodide dot for dot for 85 of 93 test labels; the rest (Orbitron, Pixelify Sans, Bungee, Monoton) differ by ~1 dot of glyph position because FreeType 2.15 (native Pillow 13) and 2.13 (Pyodide) rasterise slightly differently, which we can't control. Don't remove the pin.
- **Text is binarised** (`render._BINARY`, a 50 % threshold on the text layer's value and alpha): anti-aliased edge pixels used to go through the label-wide Floyd–Steinberg pass and came out as speckle. Measured across fonts/sizes it keeps ~97 % of the ink (a lower threshold thins small light text); `test_text_is_pure_black_and_white_before_dithering` checks every effect. Don't reintroduce gray in text layers.
- **Menus follow the platform conventions** (KDE `KStandardActions` / GNOME HIG): Print is `QKeySequence.Print` (Ctrl+P) in File, and its menu item is disabled with the button while a print runs. Edit holds Paste image (Ctrl+V; the app-wide event filter still handles the case where a *text field* has focus and the clipboard has only an image), Clear image, Clear doodle (undoable, enabled while there is a doodle), and Copy label as image (Ctrl+Shift+C: plain Ctrl+C belongs to the text fields). Use Ctrl+letter for custom shortcuts, Shift+Ctrl for the reverse, never Alt. Keyboard focus already cycles preset bar -> tabs -> page -> Output -> Print (a test pins it; don't add `setTabOrder` hacks: a second focus stop on the QTabWidget broke the cycle once).
- **Image controls live on the Image tab, including Layout.** The Content tab is only what is on the label (text, QR, the image *file*). With the default "Image only" layout the text and QR are not printed, so `MainWindow._layout_hint` says so in the status line, pointing at the Image tab. Slider/box/combo controls carry accessible names (`SliderSpin.set_name`); the row labels aren't attached to rows made of layouts, so name those controls explicitly.
- **UI details worth keeping:** checkboxes are rounded squares in every theme (round indicators read as radio buttons); one label-column width across all panels (`MainWindow._align_label_columns`, re-measured per theme because fonts differ) so fields line up between tabs and the Output box; the preview's gap strip is captioned (preview only, never exported) and the preview tooltip gives the label size.
- **Doodles** (`LabelSpec.doodle`, `doodle.py`, `widgets.DoodleCanvas`, the Doodle tab): freehand ink is a 384×224 1-bit mask stored in the spec as base64 PNG text (empty = none), so presets, `.t003label` files and the CLI carry it with no extra plumbing. `render` draws it last, over picture/QR/text alike (`render` = `_compose` + the ink), so it works with every layout. `doodle.decode` is cached (the mask is shared: never modify it) and returns None for anything damaged or not exactly W×SH. The canvas is one dot per pixel with hard-edged strokes (no anti-aliasing: the printer is 1-bit). Tools: round/square/calligraphy brushes, spray can (a timer while the button is down), line/rectangle/ellipse, paint bucket, sticker stamp, eraser; `ink` paints with a 4×4 dither tile (checker, dots, lines, diagonal) instead of solid black. Qt's own hatch brushes are not used: they are too sparse for the bucket to see an outline as closed. The bucket floods with `ImageDraw.floodfill` on a wall mask = ink + the label's own dark pixels (the underlay), walls dilated 1 dot so pattern-inked outlines are closed, and the fill is grown back 1 dot to meet them. **You draw on the preview itself, not on a separate pad:** `DoodleCanvas` is a transparent child of the preview label (`MainWindow._place_canvas` lays it over the sticker part, visible only while the Doodle tab is open), `zoom` (= `PREVIEW_SCALE`) times the label's dots, and it paints only the ink (in the theme's tint). While that tab is open the preview below it is the label *without* its doodle, so a stroke changes nothing underneath and needs no re-render; leaving the tab renders the exact printed label again. (Rendering the ink into the preview would have dithered it together with the picture; this way the one approximation is confined to the drawing tab.) The canvas hands its pen strokes to a 1:1 ink image, emits `changed` only when a stroke ends, keeps 30 undo steps, and gets the label from `set_underlay` for the bucket. The panel shows only the controls the chosen tool uses. The tab bar was tightened (padding 11 px) to fit five tabs; a test checks every theme.
- `src/t003gui/stickers.py` — the stickers: 24×24 1-bit icons drawn in code with Pillow (no image files to ship), enlarged 1-6× with nearest-neighbour, in `STICKERS` (key → title, drawer). They are stamped into the doodle ink, so once placed a sticker is just part of the drawing (no moving it afterwards). To add one: write a drawer, add it to `STICKERS`, look at it at 4× (a contact sheet is the quickest check).
- `src/t003gui/composition.py` — Qt-free `.t003label` files (JSON: `format`, `version`, `spec`, optional embedded `image`). Unlike presets (config-dir store, path only) a composition embeds its image so it travels; embedded names are sanitised and stored under a content-hash name in a temp folder. Unknown fields ignored, a newer `version` refused. The GUI's File menu (open/save/export, Ctrl+O/S/E), drag-and-drop of a `.t003label` and `t003-print --file` all use it; `core.export_png` is the image export (sticker rows only, nearest-neighbour enlarge). File dialogs are the unparented system ones (see theme.py).
- `src/t003gui/about.py` + the Help menu (in `app.py`, headed by a disabled "Version x.y.z" line): About box (version, printer found/not, bundled-font credit, repo link), "Check for updates…" (`updates.py`: on request only, one HEAD request to `github.com/<repo>/releases/latest` whose 302 target ends in the tag, compared numerically with `__version__`; shows the running version, then up to date / newer / couldn't check, with a link to the release page; no REST API, no auto-update, prereleases are never offered; tested against a local HTTP server, never GitHub), "Report an issue…", "Open presets folder". The version lives ONLY in `t003gui.__version__` (pyproject reads it dynamically; frozen builds have no package metadata); `release.yml` fails a tag that doesn't match it.
- `src/t003gui/presets.py` — Qt-free preset store, JSON at `$XDG_CONFIG_HOME/t003-label-gui/presets.json`. Shared by the GUI and `t003-print --preset NAME`.
- `src/t003gui/cli.py` — `t003-print`, installed as `~/.local/bin/print-label` by `packaging/install.sh`.
- `docs/screenshots/` — the README screenshots, rendered off-screen from the real window by `packaging/make_screenshots.py` (throwaway settings, so it never touches your own); regenerate them when the look changes.
- `packaging/` — `build.py` (PyInstaller), `make_appimage.sh`, `make_icons.py` (icon.svg → PNG/ICO/ICNS + theme arrows; outputs are committed), launcher `.desktop`, udev rule, `install.sh`.
- `.github/workflows/release.yml` — Linux (ubuntu-22.04 for old glibc), Windows, macOS-arm64 builds, each self-tested; tagging `v*` publishes a GitHub release. Windows/macOS cannot be built or hardware-tested from the Linux dev machine: CI is the only way. Windows would need the WinUSB driver (Zadig) for libusb; a spooler-based RAW path would avoid that but doesn't exist yet.

## Web UI (direction: one UI for every client; WIP on the `web-ui` branch)

The goal is a single web UI (plain HTML/JS, ES modules, **no build step, no framework**) that runs in a browser (GitHub Pages, phone) and in a desktop shell, with the Python engine behind it. **The Qt UI is frozen: bug fixes only, no new UI features**; new UI work goes in `web/`, and Qt is retired once the web UI has parity. Engine features (an effect, a font, a background) live in Python and reach both for free.

- **The parity checklist and the porting order are in [docs/web-port.md](docs/web-port.md); tick items off there.**
- **The look is data**: `web/themes.css` holds every colour, bevel, radius, font and banner detail as tokens, one block per look (Y2K Blue is `:root`; Pink overrides colours only; Gunmetal, Handheld and System define every token so nothing leaks in), chosen by `data-theme` on `<html>` (`web/themes.js`; the picker is under the Print bar and is remembered through the store seam). `web/style.css` only says where tokens go. **Never write a colour in a `style.css` rule** (a test fails) and give any new token to every look (a test fails). Keep the gel/LED/bezel vocabulary for new controls. Tokens holding a `border-color` list take one colour (flat) or four (a bevel). Handheld tints the preview and the doodle ink (`--preview-ink` / `--preview-paper`, read back by `themes.js`). Contrast was computed for every look (see `docs/web-port.md`); re-check when a palette changes. The palettes came from `src/t003gui/theme.py`, which goes away with Qt.
- **The doodle**: `web/doodle-raster.js` is the drawing engine (pure functions on a 384×224 bit grid; `node --test web/test/*.test.js`, wrapped by `tests/test_web_js.py`, which skips without Node 22+); `web/doodle.js` is the toolbar and the overlay canvas laid over the preview. While the Doodle tab is open the engine renders the label *without* its doodle and the overlay shows the ink (so drawing never waits on Python); elsewhere the engine draws the doodle into the preview. The tools, inks, limits and sticker bitmaps come from `doodle.describe()` and `api.options()`, and `tests/test_doodle.py` fails if they drift from the Qt canvas.
- **Files**: a fourth seam, `files` (`files/browser.js`: a download and the Clipboard API; `files/bridge.js`: the shell's native save dialog through `Bridge.save_file`, whose dialogs the shell injects so `bridge.py` stays toolkit-free). The label as an image is `api.export_png(spec, scale)` (sizes in `spec.EXPORT_SCALES`, names from `spec.file_stem`; Qt's export and the web page share them, and a test pins the sizes to Qt's). Future saves (`.t003label`, presets' files) go through the same seam.
- `web/main.js` + `form.js` + `index.html` + `style.css` — the UI, written once. It only talks to three seams, so nothing in it knows which client it is in: **engine** (`options()`, `preview(spec)` -> `{pixels, hints}`), **printer** (`modes`, `print(spec, {mode, address})` -> `{problems, error}`) and **store** (`get`/`set`, `store/local.js` or `store/bridge.js`). Selected by `?client=desktop`. Fonts a render opens must be in `api.fonts_needed` (a test records the real ones): the browser only has what it fetched, and a missing file silently falls back to another face.
- Browser adapters: `engine/pyodide.js` + `engine/worker.js` (Pyodide in a worker running the same `t003gui.api`; fonts fetched on demand through `api.fonts_needed`) and `printer/ble.js` (Web Bluetooth, constants from `api.options()["bluetooth"]`, writes serialised so GATT operations never overlap). Desktop adapters: `engine/bridge.js` and `printer/bridge.js`, calling `bridge.py` through pywebview.
- `web/dev_server.py` serves `web/` plus `/engine/*.py` (only `ENGINE_MODULES`, straight from `src/t003gui`), `/engine/manifest.json` and `/fonts/*`, which is the layout a published site will have. `web/desktop.py` opens the page in a pywebview window (`pip install pywebview`; not yet a project dependency). `tests/test_web.py` fails if `api` starts importing a module the browser doesn't download.
- **Known differences between the clients** (not bugs in our code): text in the four FreeType-sensitive fonts differs by about a dot (FreeType 2.13 vs 2.15), and a picture that needs a resize to a non-square size can dither differently, because Pyodide's Pillow (12.2) resamples differently from Pillow 13.0 (the browser equals Node-Pyodide exactly; same Pillow version on both sides gives identical dots). Everything else has been checked bit for bit.
- Pictures: a client writes the bytes where the engine can read them and calls `api.adopt_image(path, name)` (checks, size cap, content-hash name under the temp folder); the label then carries that path in `image_path`. Don't add per-client picture code.
- Keep `api.py` plain data in and out; the UI must never need to know about Pillow or `LabelSpec`. Run it: `python web/dev_server.py`, then http://localhost:8000. A phone reaches it with `adb reverse tcp:8000 tcp:8000` (Web Bluetooth needs https or localhost).
- Verified (2026-10): the same page printed from the browser build on Android Chrome (Web Bluetooth) and from the desktop shell (bridge, RFCOMM); the browser's pixels equal the native engine's byte for byte except the four FreeType-sensitive fonts (see the layout pin above), where they equal Node-Pyodide's. Chromium on Linux can't use Web Bluetooth with this printer (BlueZ), so test BLE from a phone.

## Hardware facts (found by calibration — don't re-derive)

- USB `0483:5743`, TSPL, bulk OUT `0x01` / IN `0x82`. Kernel 7.x has no `usblp`; no CUPS needed. Device node is group `lp`, no sudo.
- 58 mm paper, **384 printable dots** wide at 203 dpi. Label pitch is 240 dots (`SIZE 72 mm,30 mm`, `GAP 2 mm`), but the sticker is only **224 dots** (`core.SH`) tall; anything below that falls in the gap and is lost.
- TSPL `BITMAP` mode 0: bit 1 = white, 0 = black (same as Pillow mode "1").
- Status query `ESC !?`: `0x00` ready, `0x20` printing; bit flags in `core.STATUS_FLAGS`.
- **Bluetooth (probed 2026-10; RFCOMM is in the app via `bluetooth.py`, BLE only in the future web build).** Dual-mode, one public address (`T003-xxxx`), and the same TSPL goes over either transport unchanged (a test label printed correctly on both). RFCOMM needs **no pairing** (connecting with the address worked while BlueZ showed Paired/Bonded/Trusted: no):
  - *Classic SPP:* RFCOMM channel 1 (`socket.AF_BLUETOOTH`, `BTPROTO_RFCOMM`); `ESC !?` answers `00` (possibly after a stale leftover byte: drain after connecting). Sent in 512-byte chunks with a 20 ms gap (`bluetooth.RFCOMM_CHUNK` / `RFCOMM_GAP`). Needs Python's `AF_BLUETOOTH` sockets: Linux has them; macOS builds don't and Windows is untested, so `bluetooth._connect` says so instead of crashing.
  - *BLE (GATT):* write TSPL to `00002af1-…` (service `000018f0-…`, value handle `0x000b`, write + write-without-response); replies arrive as notifications on `00002af0-…` (`0x0008`). The ISSC UART (`49535343-8841-…` write, `0x0011`) also reaches the parser, and `bef8d6c9-…` (service `e7810a71-…`) gave no reply. Advertised service list differs from the real GATT database (`1800/180d/180f/fee7` advertised; `fee7` was not needed). Web Bluetooth from Android Chrome: **180-byte chunks, 5 ms gap** sends a whole label in ~0.6 s; 20 B/20 ms works but takes 16 s. Don't overlap writes (`GATT operation already in progress`).
  - *BlueZ on Linux can't open the BLE link:* `Device1.Connect` on a dual-mode device returns `BREDR.ProfileUnavailable: No more profiles to connect to` and drops the link, so Chromium and bleak fail (Android works). Only `btgatt-client -d <MAC> -t public` (direct L2CAP LE) got through; `bluetoothctl` has no usable `bearer`/`le` connect here. `ControllerMode = le` in `/etc/bluetooth/main.conf` would likely fix it but disables classic Bluetooth system-wide (untested). So on Linux use RFCOMM; a web app is for phones. (Removing the bond with `bluetoothctl remove` was needed to probe LE; RFCOMM works without it.)
